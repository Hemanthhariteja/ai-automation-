# Deployment

Deploys the backend to **Render** and the frontend to **Vercel** — both have
permanently free tiers, no credit card required, matching this project's
₹0-mandatory-budget constraint. This is a real, publicly-reachable deployment,
not a local-only setup (see `README.md` for running locally instead).

**Every step below that touches GitHub, Render, or Vercel needs your own
account** — I can prepare and verify everything in the repository, but I
can't create accounts, click "Deploy," or authorize OAuth connections on your
behalf. Follow this guide yourself; ask if any step is unclear.

## What you'll end up with

- Backend: `https://<your-service-name>.onrender.com` (FastAPI, free web service)
- Frontend: `https://<your-project-name>.vercel.app` (static React build)
- Demo Mode active by default — the deployed app works immediately with zero AI keys.

## Honest tradeoffs of the free tier (read this first)

- **Render's free web services use ephemeral disk.** Every redeploy (and
  sometimes a routine restart) wipes the SQLite file. This project turns that
  into a non-issue: set `AUTO_SEED_DEMO_DATA=true` (already the default in
  `render.yaml`) and the app reseeds ~23 synthetic The Copper Spoon leads on
  every boot if the database is empty — a visitor always sees a populated
  demo, never a blank app. **Don't enable this against data you actually want
  to keep.**
- **Render's free tier sleeps after 15 minutes of inactivity.** The first
  request after a sleep takes 30–60 seconds to wake up. This is expected —
  not a bug — and worth mentioning if you're demoing live.
- **No custom domain on the free tiers** — you get a `.onrender.com` and
  `.vercel.app` subdomain, which is fine for a college project demo.

## 1. Push the repo to GitHub

If you don't already have a GitHub repo for this project:

```bash
# from the repo root
git add -A
git commit -m "Initial commit"
```

Then create a new **empty** repository on github.com (no README/license —
this repo already has one), and:

```bash
git remote add origin https://github.com/<your-username>/<repo-name>.git
git branch -M main
git push -u origin main
```

## 2. Deploy the backend (Render)

1. Go to [render.com](https://render.com), sign up (free), connect your GitHub account.
2. **New → Blueprint**, select this repository. Render will detect `render.yaml`
   at the repo root and pre-fill everything: build command
   (`pip install -r requirements.txt`), start command
   (`uvicorn app.main:app --host 0.0.0.0 --port $PORT`), health check path
   (`/api/health`), and the environment variables listed in that file.
3. Click **Apply**. First deploy takes a few minutes. `SECRET_KEY` is
   auto-generated by Render (`generateValue: true`) — you never need to set it yourself.
4. Once live, copy the backend URL (`https://<name>.onrender.com`) — you need
   it in the next step.
5. Confirm it's actually up: `curl https://<name>.onrender.com/api/health` should
   return `{"status":"ok",...}`. If it's asleep, the first call takes a while — that's expected.

*(No `render.yaml`? You can configure the same thing by hand in the Render
dashboard: Root Directory `backend`, same build/start commands as above.)*

## 3. Deploy the frontend (Vercel)

1. Go to [vercel.com](https://vercel.com), sign up (free), connect your GitHub account.
2. **New Project**, import this repository.
3. Set **Root Directory** to `frontend` (Vercel auto-detects the Vite framework from there).
4. Under **Environment Variables**, add:
   - `VITE_API_BASE_URL` = `https://<your-render-backend-url>.onrender.com/api`
     (the exact URL from step 2, with `/api` appended — this gets baked into
     the JS bundle at build time, so it must be set *before* you deploy, not after).
5. Click **Deploy**. A few minutes later you'll have `https://<project>.vercel.app`.

## 4. Connect the two: update CORS

The backend only accepts requests from origins listed in `FRONTEND_ORIGIN`.
Right now it's still `http://localhost:5173` (the `render.yaml` default). Go
back to the Render dashboard → your service → **Environment**, and update
`FRONTEND_ORIGIN` to:

```
http://localhost:5173,https://<your-project>.vercel.app
```

(Comma-separated — this keeps local development working too.) Save, which
triggers a redeploy.

## 5. Verify the deployed demo end-to-end

Open `https://<your-project>.vercel.app` in a browser (a fresh tab — this is
a brand-new deployment, no stale dev-server cache to worry about here). You
should land on the split-screen login. Log in with the seeded demo account:

```
owner@thecopperspoon.io / demo12345
```

You should see a populated dashboard, ~23 leads, three active workflows, and
working Analytics charts — all from the auto-seed step, no manual setup.
Walk through `docs/DEMO_GUIDE.md` against this live URL to confirm everything
that works locally also works deployed.

## Database migrations on a real deployment

The default path above needs nothing extra — Render's `startCommand` boots
uvicorn, which calls `Base.metadata.create_all()` on an empty database, same
as local dev. Alembic (`backend/alembic/`, added Phase 20) matters once
you're changing the schema on a deployment that already has real data you
don't want to lose:

```bash
cd backend
alembic upgrade head
```

Run that instead of just letting the app boot, on any deploy where the DB
already exists and a migration is pending. If the DB was created the
zero-setup way before Alembic was introduced, stamp it once first (see
`docs/OPERATIONS.md`'s Database migrations section — `alembic stamp head`)
so Alembic knows it's already at the initial schema.

**The SQLite→Postgres path** the schema's types were chosen to support: add
Render's free Postgres add-on, set `DATABASE_URL` to the Postgres connection
string it gives you, add `psycopg2-binary` to `requirements.txt` (not
included today since nothing in this project uses Postgres yet), and run
`alembic upgrade head` against that URL before the app's first boot — Alembic
doesn't care which SQL dialect it's targeting, that's the entire point of
using it instead of hand-written SQL. **Honestly**: this migration path has
been tested locally against SQLite (a real backup → simulated data loss →
restore round trip, plus upgrade/downgrade/stamp all verified against a real
file), but not yet exercised against a live Postgres instance — this project
has stayed on SQLite's free-tier-friendly, zero-infrastructure path
throughout, per its own ₹0-mandatory constraint.

## Redeploying after a code change

Both Render and Vercel auto-deploy on every push to `main` by default — just
`git push`. No manual redeploy step needed.

## Rolling back / turning it off

Render and Vercel both keep a deploy history with one-click rollback in their
dashboards. To take the demo down entirely, delete the service/project from
each dashboard — this doesn't affect your local setup or GitHub repo at all.
